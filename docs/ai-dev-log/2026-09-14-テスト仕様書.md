## 2. 最大の失敗：GitHubを見ずに、設計仕様書を作り直してしまった

**今回いちばんの学びは、成果物ではなく失敗のほうにある。**

### 何が起きたか

作業開始時、Claude Code に「GitHubにアップロードしてあるので参照して」と伝えた。
ところが Claude はローカルの作業フォルダの状態（`git status`）だけを見て、

> 「設計仕様書がありません。テスト仕様書を書くには設計が必要なので、先に設計仕様書を作りましょう」

と提案してきた。もっともらしい説明（V字モデルの図つき）だったので承認したところ、
**959行の設計仕様書を新規に書き上げた。**

しかし実際には、**9月9日に自分で作った1,249行の設計仕様書が GitHub 上に存在していた**。
Claude が `git fetch`（リモートの最新を取得する操作）をしていなかったため、
手元のフォルダが古いままで、「無い」ように見えていた。

### どれくらいズレていたか

新しく作らせた設計は、既存の設計と**前提から食い違っていた**。

| 項目 | 既存（9/9・正） | Claudeが作り直した版 |
|---|---|---|
| 会員割引の計算 | 合計に5% → 税率区分へ**比例配分** | 区分ごとに5%（**1円ずれる**） |
| API構成 | BFF 7本＋バックエンド 7本の2層 | 直接6本 |
| 認証 | JWTを **httpOnly Cookie** に保管 | Authorizationヘッダ |
| エラーコード | `E-AUTH-001` 形式 | `PRODUCT_NOT_FOUND` 形式 |
| 会員コード | 10桁 | 8桁 |
| 商品コード | **8桁または13桁** | 13桁のみ |

この誤った設計に基づいて、テスト仕様書185ケースを書き上げてしまった。
**金額の期待値はほぼ全滅**で、作り直しになった。

### なぜ気づけたか

すべて書き終えて `git push` した瞬間に、
「リモートに手元にない変更があります」と拒否されて発覚した。
**push しなければ気づかないまま提出していた。**

### 対策

| # | 対策 |
|---|---|
| 1 | **作業開始時に必ず `git fetch` させる**。「GitHubを見て」と口で言うだけでは、AIはローカルしか見ないことがある |
| 2 | 「〜がありません」とAIが言ったら、**本当に無いのかを人間が確認する**。無いことを前提に大きな作業を始めさせない |
| 3 | 大きな作業の前に**一度 push しておく**。手元とリモートがずれていれば、その時点で分かる |

**AIは「無い」ことの確認が苦手**だと分かった。あるものを読むのは得意だが、
「探した範囲に無い」と「存在しない」を区別せずに報告してくる。

なお、作り直した内容は捨てる前に `wip/test-spec-discarded-20260914` ブランチへ退避した。
**AIに作業をやり直させるときは、先に退避ブランチを作らせると安全。**

## 4. AIに任せたこと

- 設計仕様書 §10 の `TC-01`〜`TC-20` を、3階層のテストケースへ詳細化
- トレーサビリティ表（設計TC → テストID、要求REQ → テストID）の機械的な突き合わせ
- 境界値の洗い出しと、各ケースの期待値の算出
- テストデータ（fixtures）の設計

### 実際に使ったプロンプトの例

**1. 期待値を手計算させず、検算スクリプトを書かせる**
```
設計仕様書 §4.4 の計算手順を、そのままPythonスクリプトに実装して。
まず設計書に載っている計算例（会員 772/38/36/28/798、非会員 772/0/37/29/838）
を入力して、一致することを確認してから、全テストケースの期待値を出して。
```
→ 手計算だと按分の余り1円を間違える。**スクリプトを設計書の例で検証してから使う**のが効いた。

**2. 「決められないこと」を勝手に決めさせない**
```
テストケースを書く過程で、設計仕様書に書かれておらず期待値を1つに決められなかった点を、
「設計仕様書への確認事項」として別セクションに列挙して。
勝手に決めて埋めないこと。
```
→ 5件出てきた（総則 §8）。前回の作り直しは、まさにAIが勝手に決めたことが原因だった。

**3. 講師の助言をテストの構造に反映させる**
```
設計仕様書の §10 テスト観点 TC-01〜TC-20 を起点にして、
単体・結合・ユーザーテストの3階層に詳細化して。
各テストケースに「設計のどのTCに対応するか」を明記すること。
```

## 5. うまくいったこと

### 期待値を「手計算」ではなく「検算スクリプト」で出した

会員割引の按分（合計に5%→区分へ比例配分→余り1円は小計が大きい区分へ）は、
手計算だと確実に間違える。設計書の計算例でスクリプトを検証してから全ケースを計算した。

これにより、**設計書には載っていない境界ケース**も見つかった。

```
  8%側の小計 510円、10%側の小計 510円、割引51円のとき
    按分：floor(51 × 510 ÷ 1020) = 25 が2つ → 合計50、余り1円
    → 「小計が大きい区分へ」というルールでは、同額のときどちらに寄せるか決まらない
```

これは設計の穴なので、勝手に決めずに**確認事項 T-1** として記録した。

### 同じ数字を4つのレベルで追いかける形にした

「おにぎり128円×2 ＋ 牛乳218円 ＋ 洗剤298円 を会員が買うと税込798円」という1ケースを、

- 単体（Backend）UT-BE-001
- 単体（Frontend）UT-FE-040
- 結合 IT-030
- ユーザーテスト UAT-002

の**4レベルすべてに同じ数値で置いた**。
どこで798円が崩れたかで、原因がサーバの計算か、画面の計算か、
APIとDBのつなぎ目か、画面表示かを切り分けられる。

### 画面とサーバで同じ計算をすることへの対策を組み込んだ

この設計は原則 P-1 により、**画面とサーバの両方に金額計算がある**（確定時に照合する）。
同じ仕様を2つの言語で実装するため、片方だけ直して食い違う事故が起きやすい。

そこで UT-BE と UT-FE に**まったく同じ入力・同じ期待値**のケースを対で置き、
どちらかがずれたら必ず落ちるようにした。

### 「付いていないこと」を確認するテストを入れた

UT-FE-076 は、`fetch` に `Authorization` ヘッダが**付いていないこと**を確認する。
設計では JWT を httpOnly Cookie に置き、JavaScript から触らせない方針のため、
ヘッダを付ける実装は設計違反になる。

**「あるべきものがある」だけでなく「あってはいけないものがない」もテストになる**と分かった。

## 6. 仲間にシェアしたいこと

### AIに「GitHubを見て」は通じないことがある

口頭で指示しても、AIはローカルのフォルダしか見ないことがある。
**作業開始時に `git fetch` を実行させる**か、自分で `git pull` してから依頼する。
今回はこれで丸1本分の作業を捨てた。

### AIが「〜がありません」と言ったら疑う

AIは「探した範囲に無い」と「存在しない」を区別せずに報告する。
**無いことを前提にした大きな提案（作り直しなど）を承認する前に、本当に無いか自分で確認する。**

### 大きな作業の前に一度 push しておく

手元とリモートがずれていれば、push した時点で分かる。
今回は全部書き終えてから push して発覚した。**最初に push していれば5分で気づけた。**

### テストの期待値は、AIに手計算させない

按分や端数処理がからむ金額は、AIも人間も手計算では間違える。
**設計書の計算例で検証したスクリプトを書かせて、それで全部計算させる**のが確実。

### 「決められないこと」を決めさせない仕組みを作る

AIは情報が足りないと、それらしい値で埋めて先に進む。
テスト仕様書に「設計仕様書への確認事項」というセクションを最初に作らせ、
**分からないものはそこに書く**ルールにした。
埋めてしまうと、テストが通っても仕様を満たしたことにならない。

### AIに作業をやり直させるときは、退避ブランチを作らせてから

`git branch wip/なんとか` を先に作らせておけば、消したものを後から取り戻せる。
「やり直して」と言う前のひと手間。

## 7. 別AIによる検証の結果

テスト仕様書を書いたセッション（Claude Opus 5）とは**別のセッション・別のモデル
（Claude Sonnet 4.5）**を2つ立て、並行して検証させた。
「褒め言葉は不要。忖度せず批判的に検査せよ」と明示的に指示した。

### 検証1：期待値の再計算と、設計仕様書との整合チェック

> **44件を検算し、44件すべて一致。計算誤りは0件。**

按分の余りの寄せ先（8%側 / 10%側）も、端数切り捨ての境界もすべて一致した。
検算スクリプトで期待値を出したのが効いた。

一方で、**設計書と突き合わせる部分**に誤りが集中していた。

### 検証2：このテスト仕様書からテストコードが書けるか

「書けますか？」と質問するのではなく、**実際に書かせて実行させた**。

> pytest 36件・jest 8件を実際に書いて実行し、**全通過**。
> 結論は「条件付きYES」。

### 検出された問題：13件

11件をその場で修正し、2件は確認事項として記録した。特に効いた指摘は次の4つ。

| 指摘 | なぜ見つからなかったか |
|---|---|
| **fixtures の `discount_type` が `"MEMBER"` だが、設計のER図の定義は `NONE` / `RATE5`** | 設計書のER図まで遡らず、それらしい値を書いていた。このままだとDBへの投入が失敗し、会員が絡むテストが全部実施不能になっていた |
| **`AmountSummary` に無い `discount_allocation` 属性をテストが前提にしていた** | 「按分の内訳を確認したい」という意図が先行し、設計にその属性が無いことを確認していなかった |
| **確認事項として挙げた T-1 を、実際に踏むテストケースが1件も無かった** | 「同額区分で余りが出る」ケースを確認事項に書いたのに、そのケース自体をテストに入れ忘れていた |
| **画面側（JavaScript）の浮動小数点誤差への対策が未規定** | サーバ側は `Decimal` を使う設計だが、画面側には `Decimal` が無いことに気づいていなかった |

### 浮動小数点の指摘を、検証して「実害なし」と確定させた

最後の指摘は、そのままでは「危ないかもしれない」で終わる。
そこで**実際に全探索して確かめた**。

```
  floor(金額 × 0.08) / floor(金額 × 0.10)  → 0〜9,999,999 の全件でズレなし
  floor(税抜合計 × 0.05)                   → 0〜9,999,999 の全件でズレなし
  按分 floor(割引 × 区分小計 ÷ 合計)        → ランダム100万通りでズレなし
```

現在の税率・割引率・金額上限の範囲では対策不要と分かった。
ただし**税率が変わったら再検証が必要**（税率は REQ-08 で変更されうる）なので、
その注意書きとあわせてテスト仕様書に残した。

**「危ないかもしれない」で止めずに、確かめて白黒つける**と、
仕様書に「なぜ対策しないのか」を根拠つきで書ける。

### この検証から得た学び

**1. 計算の検算だけでは足りない**

期待値は44件すべて正しかったのに、誤りは
**「設計書のER図に書いてあるenum値」「クラスのフィールド名」「DBのカラム名」**
といった、突き合わせる部分に集中していた。
計算が合っていても、名前が違えばテストは1行も動かない。

**2. 「未確定」と書いておくと、検証者が足りないものを教えてくれる**

「同額区分での按分の余りは未確定」と書いておいたら、
**「それを踏むテストケースが無い」**と指摘された。
分からないことを分からないと書いておくのは、後から埋めるための足場になる。

**3. 実際に動かさせると、具体的な穴が出る**

読ませて「書けそうです」と答えさせても穴は出てこない。
実行させたことで「`discount_allocation` が設計に無いので自分で足した」という
具体的な報告が返ってきた。
