## うまくいったこと

### 1. 調べられることは、AIに「実際に調べさせる」

課題の「フレームワーク・ライブラリ・OSSの脆弱性／Ver調査」を、AIの記憶で書かせると
それらしい数字が並ぶだけで根拠がない。そこで、AIに調査用のスクリプトを書かせて実行させた。

- npm registry と PyPI の API → 各パッケージの最新バージョンと**最終リリース日**
- [OSV.dev](https://osv.dev) の API → そのバージョンに既知の脆弱性があるか

結果、**`passlib` が2020年10月を最後に更新が止まっている**ことが分かった。
FastAPIのチュートリアルで広く使われているライブラリなので、調べなければそのまま採用していた。
設計仕様書では `passlib` を使わず `bcrypt` を直接呼ぶ判断に変更した。

**学び**：Ver調査は「最新版を並べる」ことではなく、**そのライブラリが今も手入れされているかを確かめる**こと。
脆弱性0件でも、更新が止まっていれば今後見つかる穴は直らない。

### 2. 「なぜそれでは足りないのか」を書かせる

対策の一覧だけなら誰でも作れる。AIに「やりがちだが不十分な対策」も並べて書かせたところ、
自分の理解が浅かった点がはっきりした。

- `docs_url=None` だけでは足りない。`/openapi.json` が生きていればAPI定義は全部読める
- 画面でボタンを隠すのは認可ではない。APIを直接叩かれれば無意味
- JWTの検証で `algorithms` を明示しないと、アルゴリズムを差し替えたトークンを通す余地が残る
- `localStorage` にトークンを置くと、XSSが1回成立した時点で読み出せる

### 3. 計算仕様は「数値例」まで書かせる

消費税の端数処理と会員割引の按分は、文章だけだと必ず解釈が割れる。
具体例（税抜772円 → 税込798円）まで仕様に入れたことで、実装時のテストケースがそのまま作れる状態になった。
フロントとバックエンドで計算結果を照合する設計なので、計算順序が仕様として固定されていないと、
バグでもないのに照合が落ちる。

### 4. 提出前に機械でチェックした

Markdownは「書けたつもり」でGitHub上で崩れることがある。提出前に2つ検証した。

| 検証 | やり方 | 結果 |
|---|---|---|
| Mermaid図が描画されるか | 10個の図をHTMLに並べてブラウザで実描画し、SVGが生成されたかをDOMで確認 | 10/10 OK |
| 文書内リンクが飛ぶか | 見出しからGitHub式のアンカーを計算し、本文中のリンクと突合 | 3件のリンク切れを発見・修正 |

リンク切れの原因は、`8.7 Swagger（OpenAPI）ドキュメントの非公開` のような見出しで、
**全角カッコが削除されるだけでハイフンには置き換わらない**というGitHubの仕様を勘違いしていたこと。
目視では絶対に気づけなかった。

## 困りごと・注意点

- **会社PCは社内プロキシ配下で、SSH（`git@github.com`）が通らなかった。**
  22番・443番とも接続不可。HTTPSでクローンして解決（git に `http.proxy` が設定済みだった）。
  同じ環境の人は `git config --global --list` でプロキシ設定を確認するのが早い。
- **AIは「もっともらしい設計」をいくらでも出す。** Lv2の要件定義でも同じ失敗をしていて、
  公式要求を読ませる前のAI出力は要求と食い違っていた。今回は要件定義書v0.2を先に読ませてから書かせた。
  **上位文書を先に読ませる工程を必ず挟む**のが、AI駆動開発でいちばん効く型だと感じている。
- 設計仕様書は分量が出る（今回1,250行）。**章立てを先に決めてから書かせる**と、
  投げる単位を分けられて手戻りが少ない。

## 仲間へのシェア

Markdownの提出物は、出す前にこの2つだけ確認するとよさそう。

1. **Mermaidは実際に描画して確かめる。** GitHub上で構文エラーになると赤いエラー枠が出る
2. **日本語見出しへのリンクは崩れやすい。** 記号（`.` `（）` `・` `：`）は削除される。
   ハイフンに置き換わるのは**半角スペースだけ**
