## 0. テストの前提

### 0.1 単体テストとの役割の違い

| | 単体テスト | 結合・機能テスト（本書） |
|---|---|---|
| 見るもの | クラス・関数1個の計算 | BFF・API・DB・ロジックをつないだ機能全体 |
| DB | 使わない | **使う**（テスト用MySQL） |
| 通信 | なし／モック | **実通信**（TestClient経由） |
| 典型的に見つかる不具合 | 計算間違い、条件の書き間違い | つなぎ間違い（DBに保存されない、エラーコードが違う、認証が効いていない、**画面とサーバの計算がずれる**） |

**このレベルでしか見つからない不具合の例**

- 計算は正しいのにDBに保存する列を間違えている
- 単体では例外を投げているのに、API層が500を返している（400のはずが）
- 認証チェックを付け忘れたAPIがある
- **画面の計算とサーバの計算がずれ、`E-TXN-001` で誰も購入できない**

### 0.2 テストデータ

テストごとにDBを初期化し、[`fixtures/`](fixtures/) のCSVを投入する。
初期化と投入は `src/backend/tests/conftest.py` の fixture が行う。

## 6. 金額照合（IT-050〜053）★セキュリティの中核

対応：原則 P-1 / 設計 §8.6 / NFR-SEC-04

**設計仕様書 §8.6 が課題「Backendでも計算のロジックを入れて、Frontendの計算値と照合」への回答であり、
本節がその検証にあたる。**

| ID | 設計TC | 観点 | 操作 | 期待 | なぜこの確認が要るか |
|---|---|---|---|---|---|
| IT-050 | **TC-13** | ★合計額の改ざん | `clientAmount.total` を **0** に書き換えて確定リクエストを送る | **400** `E-TXN-001`。**DBに何も保存されない**（`transactions` が0件） | 画面のJavaScriptは書き換えられる。0円で購入確定を送られても弾けなければならない |
| IT-051 | **TC-14** | ★単価の混入 | リクエストに `unitPrice: 1` を追加して送る | 追加した値は**無視**され、マスタの単価（128円）で計算される。結果は **798円** | 設計 §5.5 の `CheckoutLineIn` に `unit_price` を**定義していない**ため、送られても無視される。型の形として事故が起こりえないこと |
| IT-052 | | 5項目すべてを照合 | `clientAmount` の **`discount` だけ**を1円ずらして送る（他4項目は正しい） | **400** `E-TXN-001` | 設計 §8.6 手順4「5項目すべてが一致することを確認する」。`total` だけ照合していると、内訳のずれを見逃す |
| IT-053 | | サーバ計算値の返却 | IT-050 の応答内容を確認 | 応答に**サーバが計算した正しい金額**が含まれる | 設計 ER-5。画面を正しい値に更新できる。単に拒否するだけでは、レジ担当が同じ操作を繰り返すことになる |

**IT-052 の意図**：照合が「合計だけ」だと、8%の税が1円多く10%の税が1円少ない、
といった**相殺して合計が合うずれ**を見逃す。内訳がずれたまま保存されると、
後から税区分別の売上を集計したときに合わなくなる。

## 7. 税率可変（IT-060〜063）

対応：REQ-08 / F-12 / A-06, B-05 / NFR-OPS-04

**要求 REQ-08「税率を可変できる」の検証。**
合格基準は「税率が変えられること」ではなく、
**「プログラムを1行も修正せず、マスタの変更だけで変えられること」**。

**基準日の与え方**：税率は「その日に有効な行」をマスタから引く。
改定日をまたぐテストは **システム日付を固定して**実施する（`freezegun` の `@freeze_time`）。

| ID | 設計TC | 観点 | 操作 | 期待 | なぜこの確認が要るか |
|---|---|---|---|---|---|
| IT-060 | **TC-05** | ★税率改定 | `tax_rates` に `(REDUCED, 2027-04-01, 0.01)` を**1行追加**（コード変更・再起動なし）。システム日付を **2027-04-01** に固定しておにぎり×1を確定 | 税 **1円**、税込 **129円**（`128×0.01=1.28` → 切り捨て1） | NFR-OPS-04 の中核。コードに 0.08 が埋め込まれていると、この行を追加しても結果が変わらず失敗する |
| IT-061 | | 適用日の境界（前日） | 同じ状態で、システム日付を **2027-03-31** に固定 | **0.08 が適用**される（税10円・税込138円） | 「その日に有効な行」を選ぶロジックの境界値。改定日の前日は旧税率 |
| IT-062 | | 適用日の境界（当日） | システム日付を **2027-04-01** に固定 | **0.01 が適用**される | 改定日当日から新税率。IT-061 との対で切り替わりを確認する |
| IT-063 | **TC-06** | 過去取引の保持 | IT-060 の改定**前**に確定した取引の明細を確認 | `applied_tax_rate` が **0.08 のまま** | 設計 D-1 / 原則 P-3。税率改定で過去の履歴が書き換わらないこと |

## 8. pytest 実装の指針

```python
import pytest
from freezegun import freeze_time
from tests.conftest import login, insert_tax_rate, make_checkout_request

ONIGIRI = "4901234567894"   # 128円 軽減8%
MILK    = "4901234567900"   # 218円 軽減8%
SOAP    = "4902345678901"   # 298円 標準10%
MEMBER  = "1000000001"


# IT-007：存在しないIDでも、パスワード誤りと同じメッセージを返す（ER-4）
def test_it_007_unknown_id_returns_same_message_as_wrong_password(client):
    wrong_pw = client.post("/api/login", json={"loginId": "cashier01", "password": "xxxx"})
    unknown  = client.post("/api/login", json={"loginId": "unknown99", "password": "xxxx"})
    assert wrong_pw.status_code == unknown.status_code == 401
    assert wrong_pw.json()["code"] == unknown.json()["code"] == "E-AUTH-001"
    # メッセージが同一であること（IDの実在を外部に漏らさない）
    assert wrong_pw.json()["message"] == unknown.json()["message"]


# IT-005（TC-16）：セッションCookieは httpOnly であること
def test_it_005_session_cookie_is_httponly(client):
    res = client.post("/api/login", json={"loginId": "cashier01", "password": TEST_PASSWORD})
    set_cookie = res.headers["set-cookie"]
    assert "HttpOnly" in set_cookie   # JavaScriptから読めない
    assert "SameSite" in set_cookie


# IT-030（TC-01）：設計§4.4の計算例が、API経由・DB保存後も同じ値になる
def test_it_030_checkout_member_mixed_tax(logged_in_client, db):
    payload = make_checkout_request(
        lines=[(ONIGIRI, 2), (MILK, 1), (SOAP, 1)], member_code=MEMBER,
    )
    res = logged_in_client.post("/api/transactions", json=payload)
    assert res.status_code == 201

    saved = db.fetch_one("SELECT * FROM transactions ORDER BY transaction_id DESC LIMIT 1")
    assert saved["subtotal"] == 772
    assert saved["discount_amount"] == 38
    assert saved["tax_reduced"] == 36     # 按分の余り1円が8%側へ寄った結果
    assert saved["tax_standard"] == 28
    assert saved["total"] == 798


# IT-050（TC-13）：合計を0に改ざんしても保存されない（§8.6）
def test_it_050_tampered_total_is_rejected(logged_in_client, db):
    payload = make_checkout_request(lines=[(ONIGIRI, 2)], member_code=MEMBER)
    payload["clientAmount"]["total"] = 0          # 画面のJSを書き換えた想定
    res = logged_in_client.post("/api/transactions", json=payload)
    assert res.status_code == 400
    assert res.json()["code"] == "E-TXN-001"
    # 何も保存されていないこと
    assert db.fetch_val("SELECT COUNT(*) FROM transactions") == 0


# IT-051（TC-14）：unitPrice を混ぜても無視され、マスタの単価で計算される
def test_it_051_client_supplied_price_is_ignored(logged_in_client):
    payload = make_checkout_request(
```
