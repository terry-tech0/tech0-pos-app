## 0. テストの前提

### 0.1 計算仕様（設計仕様書 §4.4 の再掲）

**すべての期待値はこの手順で算出している。** `floor` は切り捨て。

```
1. 行金額      = 単価 × 数量（税抜・整数円）
2. subtotal   = Σ 行金額
3. discount   = floor(subtotal × 0.05)          ← 会員のみ。非会員は 0
4. 区分ごとの割引 = floor(discount × 区分の税抜小計 ÷ subtotal)   ← 比例配分・切り捨て
   配分の余り（discount − 配分額の合計）は、税抜小計が大きい区分に加算する
5. 区分ごとの割引後税抜 = 区分の税抜小計 − 配分された割引
6. 区分ごとの消費税     = floor(割引後税抜 × その区分の税率)
7. total      = (subtotal − discount) + 消費税の合計
```

**手順3と手順4の関係が本仕様の要点。**
割引は「先に合計へ5%を掛けてから区分へ配分する」のであって、
「区分ごとに5%を掛ける」のではない。この2つは結果が1円違うことがある。

### UT-BE-001 の計算過程（基本形のため詳述）

```
1. 行金額     : おにぎり 128×2 = 256（8%）  牛乳 218×1 = 218（8%）  洗剤 298×1 = 298（10%）
2. 税抜合計   : 256 + 218 + 298 = 772
3. 会員割引   : floor(772 × 0.05) = floor(38.6) = 38
   区分別小計 : 8% = 256 + 218 = 474     10% = 298
4. 按分（8%） : floor(38 × 474 ÷ 772) = floor(23.33) = 23
   按分（10%）: floor(38 × 298 ÷ 772) = floor(14.67) = 14
   配分の余り : 38 − (23 + 14) = 1 → 小計が大きい 8%（474 > 298）へ → 8%は 24
5. 割引後税抜 : 8% = 474 − 24 = 450       10% = 298 − 14 = 284
6. 消費税     : floor(450 × 0.08) = floor(36.0) = 36
                floor(284 × 0.10) = floor(28.4) = 28
7. 税込合計   : (772 − 38) + (36 + 28) = 734 + 64 = 798
```

### UT-BE-014 と UT-BE-015 が同じ税込20円になる理由（直感に反するので補足）

```
19円: 割引 0円 → 課税対象 19円 → 税 floor(1.52)=1 → 19 + 1 = 20円
20円: 割引 1円 → 課税対象 19円 → 税 floor(1.52)=1 → 19 + 1 = 20円
```

税抜が1円違っても、割引の切り捨てにより課税対象が同じ19円になるため請求額が一致する。
**仕様どおりの挙動であり、バグではない。**

## 7. 不変条件（UT-BE-053〜056）

個別の値ではなく「**どんな入力でも必ず成り立つ性質**」を検証する。

| ID | 検証する条件 | なぜ必要か |
|---|---|---|
| UT-BE-053 | `total == subtotal − discount + taxReduced + taxStandard` | 画面に出す5つの数字が互いに矛盾しないこと。レジで最も信用を失う不具合はここ |
| UT-BE-054 | `taxReduced` と `taxStandard` が**それぞれ**期待値と一致すること（合計だけで判定しない） | 設計 §3.4 の `AmountSummary` に按分の内訳は含まれず、`allocateDiscount` は private のため、按分は**外から直接見えない**。税額の内訳を個別に確認することで、按分の誤りを間接的に検出する。合計だけ見ると、8%が1円多く10%が1円少ないといった**相殺して合計が合うずれ**を見逃す |

## 9. pytest 実装の指針

本仕様書からテストコードを書くときの方針。**表の1行が、コードの1ケースに対応する。**

```python
import pytest
from decimal import Decimal
from services.amount_calculator import AmountCalculator
from schemas.pos import CheckoutLineIn

R, S = "REDUCED", "STANDARD"
RATES = {R: Decimal("0.08"), S: Decimal("0.10")}


def line(unit_price, quantity, category=R):
    """テスト用の明細を作るヘルパー"""
    return dict(unit_price=unit_price, quantity=quantity, tax_category=category)


# UT-BE-001：設計仕様書 §4.4 の計算例（基本形）
def test_ut_be_001_member_mixed_tax():
    result = AmountCalculator().calculate(
        [line(128, 2, R), line(218, 1, R), line(298, 1, S)],
        is_member=True, tax_rates=RATES,
    )
    assert result.subtotal == 772
    assert result.discount == 38
    assert result.tax_reduced == 36
    assert result.tax_standard == 28
    assert result.total == 798


# UT-BE-011, 012：按分の余り1円が「小計の大きい区分」へ寄ることの確認
@pytest.mark.parametrize(
    "test_id, lines, expected_tax_reduced, expected_tax_standard, expected_total",
    [
        # 8%側の小計が大きい（333 > 100）→ 余り1円は8%へ → 割引後 316 → 税25
        ("UT-BE-011", [line(333, 1, R), line(100, 1, S)], 25, 9, 446),
        # 10%側の小計が大きい（333 > 100）→ 余り1円は10%へ → 割引後 316 → 税31
        ("UT-BE-012", [line(100, 1, R), line(333, 1, S)], 7, 31, 450),
    ],
)
def test_discount_allocation_remainder(test_id, lines, expected_tax_reduced,
                                       expected_tax_standard, expected_total):
    result = AmountCalculator().calculate(lines, is_member=True, tax_rates=RATES)
    assert result.total == expected_total, f"{test_id} 税込合計"
    # 按分の内訳は AmountSummary から直接は見えないため、税額の内訳で確認する
    # （合計だけ見ていると、8%と10%が両方ずれて相殺された場合に気づけない）
    assert result.tax_reduced == expected_tax_reduced, f"{test_id} 8%分の消費税"
    assert result.tax_standard == expected_tax_standard, f"{test_id} 10%分の消費税"


# UT-BE-020〜023：端数処理の境界（表をそのままパラメータ化する）
@pytest.mark.parametrize(
    "test_id, unit_price, category, expected_tax, expected_total",
    [
        ("UT-BE-020", 12, R, 0, 12),   # 12×0.08 = 0.96 → 0
        ("UT-BE-021", 13, R, 1, 14),   # 13×0.08 = 1.04 → 1
        ("UT-BE-022",  9, S, 0,  9),   #  9×0.10 = 0.90 → 0
        ("UT-BE-023", 10, S, 1, 11),   # 10×0.10 = 1.00 → 1
    ],
)
def test_tax_rounding_boundary(test_id, unit_price, category, expected_tax, expected_total):
    result = AmountCalculator().calculate(
        [line(unit_price, 1, category)], is_member=False, tax_rates=RATES,
    )
    assert result.tax_reduced + result.tax_standard == expected_tax, f"{test_id} 消費税"
    assert result.total == expected_total, f"{test_id} 税込合計"


# UT-BE-043, 044：商品コードは 8桁 or 13桁のみ。「間」の桁数は弾く
@pytest.mark.parametrize("code", ["456789012", "456789012345"])
def test_product_code_between_8_and_13_is_rejected(code):
    with pytest.raises(ValueError):
        CheckoutLineIn(product_code=code, quantity=1)


# UT-BE-053, 054：不変条件（UT-BE-001〜018 の全ケースで成立すること）
@pytest.mark.parametrize("lines, is_member", ALL_CALC_CASES)
def test_invariants(lines, is_member):
    r = AmountCalculator().calculate(lines, is_member=is_member, tax_rates=RATES)
    assert r.total == r.subtotal - r.discount + r.tax_reduced + r.tax_standard  # UT-BE-053
    # UT-BE-054：按分の内訳は AmountSummary に含まれない（allocateDiscount は private）。
    # 税額の内訳を個別に確認することで、按分の誤りを間接的に検出する
    assert r.tax_reduced == expected_tax_reduced
    assert r.tax_standard == expected_tax_standard
```

**方針**

- テストIDをテスト関数名またはパラメータに必ず含め、失敗時にどのケースか分かるようにする
- 境界値は `@pytest.mark.parametrize` で表形式に書き、**本仕様書の表と1対1で対応**させる
- 期待値はコードで計算せず、**本仕様書の値を直接書く**
  （テストコード内で計算すると、実装と同じ間違いをして両方通ってしまう）
- 按分のテストでは**内訳まで確認する**。合計だけ見ていると、8%と10%が両方ずれて相殺された場合に気づけない
