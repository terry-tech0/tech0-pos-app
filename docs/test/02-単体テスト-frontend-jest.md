## 0. テストの前提

### 0.1 ケースの並び順

いちばん基本的な正常系から始め、徐々に周辺へ広げる。

**「商品が1つ追加される」→「数量が変更できる」→「削除できる」→「画面の状態」→「金額計算」→「入力検証」→「表示整形」→「通信（モック）」→「画面操作」**

### 0.2 なぜ通信をモックするのか（非エンジニア向け）

単体テストは「関数1個が正しいか」を見るもの。
本物のサーバーに通信すると、サーバーが起動していない・DBの中身が変わった等、
**関数のバグとは無関係な理由で落ちる**ようになる。
そこで「こう聞かれたらこう答える」という替え玉（モック）に差し替える。
本物の通信を通す確認は、結合テスト（[03-結合機能テスト.md](03-結合機能テスト.md)）の役割。

### 0.3 このアプリ特有の注意：画面にも金額計算がある

設計仕様書の原則 P-1 により、**画面は表示用に金額を計算し、確定時にサーバの計算値と照合される**。
つまり画面側にも §4.4 の計算仕様がそのまま実装される。

**§4 の金額計算テスト（UT-FE-040〜044）は、Backend の UT-BE-001, 002, 011, 012, 020, 021 と
まったく同じ入力・同じ期待値**にしてある。
どちらか片方の実装がずれたら、必ずどちらかのテストが落ちるようにするため。

### 0.4 画面側の計算と浮動小数点について

JavaScript の数値（`number`）は小数を正確に表せない（`0.1 + 0.2 !== 0.3`）。
サーバ側は `Decimal` を使う設計（§4.2）だが、**画面側には `Decimal` がない**。
そのため「画面の計算だけ1円ずれて `E-TXN-001` が出続ける」事故が起こりうるかを、
本仕様書の作成時に検証した。

| 検証内容 | 結果 |
|---|---|
| `floor(金額 × 0.08)` と `floor(金額 × 0.10)` を **0〜9,999,999 の全件**で確認 | **ズレなし** |
| `floor(税抜合計 × 0.05)`（会員割引）を **0〜9,999,999 の全件**で確認 | **ズレなし** |
| 按分 `floor(discount × 区分小計 ÷ subtotal)` を**ランダム100万通り**で確認 | **ズレなし** |

**結論**：現在の税率（8% / 10%）・割引率（5%）・金額上限（9,999,999円）の範囲では、
`number` で計算しても切り捨て後の結果は `Decimal` と一致する。画面側で特別な対策は不要。

> **ただし税率が変わったら再検証が必要。** 税率は要求 REQ-08 により変更されうる（例：食品1%）。
> 割り切れない税率（1/3 など）が設定された場合、この結論は成立しない可能性がある。
> 税率マスタを変更したときは、この検証をやり直すこと。

対応：設計仕様書 §4.4（画面側の実装）、原則 P-1

describe("BFFの呼び出し（通信はモック）", () => {
  beforeEach(() => {

  });
  afterEach(() => {

  });

  test("UT-FE-070 200なら商品が返る", async () => {

**方針**

- テストIDをテスト名の先頭に置き、失敗時に本仕様書のどのケースか分かるようにする
- 境界値は `test.each` で表形式に書き、**本仕様書の表と1対1で対応**させる
- 金額計算のケースは、**Backend と同じ数値をそのまま書く**（片方だけ直したときに気づけるように）
- `global.fetch = jest.fn()` で通信を差し替え、`afterEach` で必ず初期化する
  （替え玉を残したまま次のテストへ行くと、別のテストが謎の失敗をする）
