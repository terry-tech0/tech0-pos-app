## 1. 本書の位置づけ（V字モデル）

### 1.1 左側の文書と右側のテストの対応

```
  【左側：作る前に決める】                  【右側：決めた通りか確かめる】

  要求（講座配布の要求定義書）  ←────────→  ④ ユーザーテスト（UAT）
     REQ-01〜11                              「レジ担当が業務を回せるか」
        │                                     文書：04-ユーザーテスト.md
        ▼                                              ▲
  要件定義書 §3 機能要件        ←────────→  ③ 結合・機能テスト（IT）
     F-01〜12                                「BFF・API・DBがつながって動くか」
        │                                     文書：03-結合機能テスト.md
        ▼                                              ▲
  設計仕様書（クラス・API・DB） ←────────→  ① ② 単体テスト（UT）
     §3.4 クラス図 / §4.4 計算仕様            「関数1個が仕様どおり値を返すか」
     §5 API / §6 入力上下限                   文書：01-, 02-
        │                                              ▲
        └──────────── 実装（コード）──────────┘
```

**左側の文書と右側のテストは1対1で対応する。**
「設計に書いていないことはテストできない」「テストで落ちたら、どの文書に戻ればよいかが分かる」
という2つの利点がある。

| どのテストで落ちたか | 戻るべき場所 |
|---|---|
| 単体テスト | 実装コード、または設計仕様書 §3.4 クラス図 / §4.4 計算仕様 |
| 結合・機能テスト | 設計仕様書 §5 API設計 / §4.2 テーブル定義 |
| ユーザーテスト | 要件定義書の機能要件、または要求そのものの理解 |

### 1.2 テストレベルの定義

| レベル | 略号 | 何を確かめるか | 実行方法 | DB | 画面 |
|---|---|---|---|---|---|
| 単体テスト（Backend） | UT-BE | クラス・関数1個が、与えた入力に対し仕様どおりの値を返すか | `pytest` | 使わない | 開かない |
| 単体テスト（Frontend） | UT-FE | 関数1個・部品1個が仕様どおり動くか | `jest` | 使わない | 開かない（通信はモック） |
| 結合・機能テスト | IT | BFF・バックエンド・DBをつないで機能として成立するか | `pytest`（TestClient）＋テスト用DB | 使う | 開かない |
| ユーザーテスト | UAT | レジ担当が実際の業務手順を最後まで完了できるか | 人が手で操作 | 使う | 開く |

**「モックする」とは（非エンジニア向け）**
本物のサーバーに通信する代わりに、「こう聞かれたらこう答える」という替え玉を用意すること。
単体テストでは、サーバーが落ちていてもテストが失敗しないよう通信部分を替え玉に差し替える。
通信を本物にした瞬間、それは単体テストではなく結合テストになる。

### 1.3 このアプリ特有の事情：計算が2か所にある

設計仕様書の原則 P-1 により、**金額計算は画面とサーバの両方に実装される**。

```
   画面（TypeScript）          サーバ（Python）
   表示用に計算              ← 確定時に計算し直す
        │                              │
        └──── 5項目すべて一致するか照合 ────┘
                    │
            1つでも違えば E-TXN-001 で保存しない
```

このため、テストも次の3方向から必要になる。

| # | 確かめること | 担当するテスト |
|---|---|---|
| 1 | **サーバの計算**が §4.4 の手順どおりか | UT-BE（`AmountCalculator`） |
| 2 | **画面の計算**が §4.4 の手順どおりか | UT-FE（画面側の計算関数） |
| 3 | **2つの計算結果が一致**し、食い違えば保存を止めるか | IT（金額照合） |

**同じ計算仕様を2つの言語で実装するため、片方だけ直して食い違う事故が起こりやすい。**
本書では、UT-BE と UT-FE で**まったく同じ入力・同じ期待値**のケースを対で用意し、
どちらかがずれたら必ず落ちるようにしている。

## 2. テスト技法

講義で扱った技法を、本プロジェクトでどう使うかを定義する。

### 2.1 同値分割

入力を「同じ結果になるグループ」に分け、各グループから代表を1つ選んでテストする。
例：数量の入力（設計仕様書 §6 より 1〜99）

| グループ | 範囲 | 代表値 | 期待 |
|---|---|---|---|
| 有効同値 | 1〜99 | 50 | 正常に受け付ける |
| 無効同値（小さすぎ） | 0以下 | 0, −1 | `E-VAL-002` |
| 無効同値（大きすぎ） | 100以上 | 100 | `E-VAL-002` |
| 無効同値（型違い） | 小数・文字列 | 2.5, "あ" | `E-VAL-002` |

1〜99 の全99通りを試す必要はない。50が通れば37も通ると考えてよい。
ただし**端（境界）だけは別扱い**にする。それが次の境界値分析。

### 2.2 境界値分析

バグは「範囲の境目」で起きやすい。`<` と `<=` の書き間違いが典型例。
有効範囲の**すぐ外・端・端・すぐ外**の4点を必ずテストする。

```
   0        1              99       100
   ↑        ↑               ↑        ↑
 下限外    下限            上限     上限外
  NG       OK              OK       NG
```

本プロジェクトの境界値一覧（設計仕様書 §6 入力値の下限・上限より）

| 対象 | 下限外 | 下限 | 上限 | 上限外 | エラーコード |
|---|---|---|---|---|---|
| 担当ログインID | 3文字 | 4文字 | 20文字 | 21文字 | `E-VAL-001` |
| パスワード | 7バイト | 8バイト | 72バイト | 73バイト | `E-VAL-001` |
| 会員識別番号 | 9桁 | 10桁 | 10桁 | 11桁 | `E-VAL-001` |
| 商品コード（JAN） | 7桁 | **8桁** | **13桁** | 14桁 | `E-VAL-001` |
| 1行あたりの数量 | 0 | 1 | 99 | 100 | `E-VAL-002` |
| 1会計の明細行数 | 0 | 1 | 100 | 101 | `E-VAL-003` / `E-TXN-002` |
| 単価（商品マスタ） | −1 | 0 | 999,999 | 1,000,000 | `E-VAL-001` |
| 税抜・税込合計 | （なし） | 0 | 9,999,999 | 10,000,000 | **未確定（確認事項 T-3）** |

**商品コードの境界が2つある点に注意**：JANは 8桁 または 13桁 のどちらかのみ有効で、
その**間の9〜12桁は無効**。「8以上13以下」と実装すると10桁が通ってしまう。
この誤りを検出するケースを必ず置く（UT-BE-041〜046）。

### 2.3 金額計算の境界値（本プロジェクト固有）

消費税と会員割引はどちらも**切り捨て**のため、「0円のままか、1円になるか」が変わる線が存在する。

| 境界 | 計算 | 結果 | 検出できる誤り |
|---|---|---|---|
| 課税対象 12円 × 8% | 0.96円 | **0円** | 四捨五入で実装している |
| 課税対象 13円 × 8% | 1.04円 | **1円** | 同上 |
| 課税対象 9円 × 10% | 0.90円 | **0円** | 同上 |
| 課税対象 10円 × 10% | 1.00円 | **1円** | 同上 |
| 税抜合計 19円 × 5%割引 | 0.95円 | **0円** | 割引の端数処理 |
| 税抜合計 20円 × 5%割引 | 1.00円 | **1円** | 同上 |

さらに、**割引の按分に固有の境界**がある（設計仕様書 §4.4 手順4）。

```
  会員割引38円を、8%小計474円と10%小計298円に比例配分する
    8%分  : floor(38 × 474 ÷ 772) = floor(23.33) = 23
    10%分 : floor(38 × 298 ÷ 772) = floor(14.67) = 14
    配分の合計 23 + 14 = 37 ≠ 38  ← 切り捨てにより1円余る
    余った1円は「税抜小計が大きい区分」（8%）へ → 8%は24
```

**この「余り1円」の処理がバグの温床**であり、実装が余りを捨てると
割引額の合計と内訳が1円合わなくなる。専用のケースを置く（UT-BE-020〜026）。

### 2.4 正常系・異常系

| 系 | 定義 | 本プロジェクトでの例 |
|---|---|---|
| 正常系 | 想定どおりの使い方をした場合 | 登録済み商品を読み、購入する |
| 異常系（入力） | ユーザーが誤った値を入れた場合 | 9桁の会員番号、数量0、未登録商品 |
| 異常系（状態） | システム側の状態が想定外の場合 | トークン期限切れ、バックエンド停止 |
| 異常系（悪意） | 攻撃的な入力 | `total: 0` に書き換えた確定リクエスト、SQL断片 |

**異常系テストの合格基準は「エラーになること」ではなく「正しくエラーになり、業務が続けられること」。**
設計仕様書の方針 ER-1「エラーで購入リストを消さない」がまさにこれで、
未登録商品を読んだときに**リストの他の商品が消えない**ことまで確認する。

### 2.5 テスト観点 × 技法の対応表

| 観点 | UT-BE | UT-FE | IT | UAT |
|---|---|---|---|---|
| 正常系 | ● | ● | ● | ● |
| 境界値 | ● | ● | ● | ●（数量99など操作可能なもの） |
| 異常値（入力） | ● | ● | ● | ● |
| 異常系（状態） | ○（トークン期限切れ） | ○（通信失敗のモック） | ● | ●（セッション切れ・停止） |
| 異常系（悪意） | （なし） | （なし） | ●（金額改ざん・SQL断片） | （なし） |
| 画面と サーバの計算一致 | ● | ● | ● | （なし） |
| 業務の流れ | （なし） | （なし） | ○ | ● |
| 操作性・所要時間 | （なし） | （なし） | （なし） | ● |

● 主に担当する ／ ○ 一部担当する

## 6. 合否判定基準

### 6.1 個別ケースの判定

| 判定 | 条件 |
|---|---|
| 合格（PASS） | 期待結果と実際の結果が完全に一致した |
| 不合格（FAIL） | 一致しなかった |
| 保留（BLOCKED） | 前提条件が整わず実施できなかった |
| 対象外（N/A） | 仕様変更等により不要になった |

### 6.2 リリース判定（Lv2完成とみなす基準）

| # | 基準 |
|---|---|
| 1 | 単体テスト（UT-BE / UT-FE）が **全件合格**。1件でもFAILがあれば不合格 |
| 2 | 結合・機能テスト（IT）が **全件合格** |
| 3 | ユーザーテスト（UAT）の必須シナリオ（UAT-001〜012）が **全件合格** |
| 4 | 設計仕様書 §10 の **TC-01〜TC-20 すべてに、合格したテストケースが1件以上**紐づいている |
| 5 | 要求 REQ-01〜11 のすべてに、合格したテストケースが1件以上紐づいている（§7で確認） |
| 6 | セキュリティ観点（TC-13〜TC-18）に対応するテストが全件合格 |
| 7 | **§8 の確認事項 T-1〜T-7 がすべて設計側で確定**し、期待値が「（確定後に記入）」のケース（UT-BE-019, UT-BE-036, UT-BE-039b, UAT-012 手順2）に具体的な期待値が入っていること |

> **基準7を置く理由**：期待値が未確定のケースは、合格とも不合格とも判定できない。
> 「テストは全部通った」と言えても、**仕様を満たしたことの証明にはならない**。
> 未確定のまま実装を進めると、実装者が独自に埋めた解釈がそのまま仕様になってしまう。

## 9. テスト実施記録の書き方

各詳細文書のケース表に「実施日／実施者／結果／備考」の列を設け、実施のたびに記入する。
**未実施の段階では空欄のままにする**（実施していないものを「合格」と書かない）。

不具合を見つけた場合は以下を記録する。

| 項目 | 記入内容 |
|---|---|
| 発見したテストID | UT-BE-020 など |
| 現象 | 期待 24 に対し 23 が返った |
| 原因 | 按分の余り1円を捨てていた |
| 原因の所在 | 実装のみ ／ 設計仕様書の誤り ／ 要件定義書の誤り |
| 対応 | 修正内容と、上流文書を直した場合はその版 |

**「原因の所在」を必ず記録する**のがV字モデルの肝。
設計や要件の誤りが原因なら、コードだけ直しても同じ不具合が再発する。

### 10.4 浮動小数点についての検証（指摘10への対応）

サーバ側は `Decimal` を使う設計（§4.2）だが、**画面側の JavaScript には `Decimal` がない**。
「画面の計算だけ1円ずれて `E-TXN-001` が出続け、誰も購入できない」事故が起こりうるかを検証した。

| 検証内容 | 結果 |
|---|---|
| `floor(金額 × 0.08)` / `floor(金額 × 0.10)` を **0〜9,999,999 の全件** | **ズレなし** |
| `floor(税抜合計 × 0.05)` を **0〜9,999,999 の全件** | **ズレなし** |
| 按分 `floor(discount × 区分小計 ÷ subtotal)` を**ランダム100万通り** | **ズレなし** |

現在の税率・割引率・金額上限の範囲では対策不要と判断した。
ただし**税率が変わったら再検証が必要**（要求 REQ-08 により税率は変更されうる）。

### 10.5 この検証から得た学び

- **同じAIに「合ってる？」と聞いても意味が薄い**。自分の出力を肯定しがちなため、
  別セッション・別モデルで「批判的に検査せよ」「褒め言葉は不要」と明示的に指示した
- 計算そのものは44件すべて正しかったが、**設計書と突き合わせる部分**（ER図のenum値、
  カラム名、クラスのフィールド）に誤りが集中していた。
  計算の検算だけでは見つからない種類の誤りである
- 「コードが書けるか」は**実際に書かせて実行させる**のが最も効く。
  読んで「書けそう」と答えさせても穴は出てこない。
  実行させたことで「`discount_allocation` が設計に無いので自分で足した」という
  具体的な報告が返ってきた
- **「未確定」と書いておくと、検証者が「それを踏むテストが無い」と指摘してくれた**（指摘6）。
  分からないことを分からないと書いておくのは、後から埋めるための足場になる
